# Session 120 — COMP-TRACKER-FORGEJO

**Date:** 2026-09-18
**Feature:** `COMP-TRACKER-FORGEJO`

## What happened

Design, blueprint, and plan for COMP-TRACKER-FORGEJO had already been written and reviewed (5 Codex adversarial rounds) in a prior session, which ended waiting on the human's go-ahead to implement. This session picked up from that resume note, registered the feature on the roadmap (it hadn't been scaffolded yet, per convention for a pre-implementation design/blueprint/plan-stage feature), and dispatched all 8 tasks from plan.md to Codex per this repo's hard rule that Claude orchestrates and never writes real code itself. T1 (Forgejo transport) and T2 (lifecycle-derivation pure function) went out in parallel since they're independent. T3 (registering forgejo as a first-class provider across four GitHub-only surfaces plus the schema) went alone, escalated to gpt-6-astra/medium as the highest-risk correctness surface everything else depends on. Once T3 landed, T4 (validator resolution), T5 (push extension), and T6 (promotion command) went out concurrently in the SAME working tree, each scoped to disjoint files with explicit 'touch only these files' instructions in the brief -- all three came back clean with zero file collisions. T7 (MCP surface) followed once T3+T6 were in. Every dispatch's test claims were verified locally (not just trusted) before committing, and each task landed as its own commit.

T8 (the E2E/review/coverage-sweep step) is where the loop earned its keep: a merge-gate adversarial review of the full T1-T7 diff (gpt-6-astra/medium) found three real gaps that all seven task-level test suites had missed because each was individually green -- the CLI silently reported failed Forgejo writes as successful (a 503 on both writes printed 'Pushed... (wrote)' and exited 0), multi-label partial success collapsed into one boolean losing which specific label actually wrote, and design.md's own explicitly-required end-to-end test (MCP link_features -> feature.json -> both runExternalRefChecks and xref-push agreeing on derive_expect) was simply never written -- existing tests either only checked schema acceptance or hand-built the link object, skipping the MCP hop. All three were verified against the live code before dispatching a fix, the fix was verified locally, and a round-2 Codex review targeted specifically at the fix commit came back REVIEW CLEAN. Feature marked COMPLETE through record_completion (the completion gate), not a raw status write -- deliberately, since this feature's own Piece 3 is about exactly that distinction mattering.

## What we built

lib/tracker/forgejo-api.js (new) -- Forgejo/Gitea transport, base URL pinned at construction, bearer token never forwarded cross-origin, labels additive-only (never read-then-replace). lib/status-projection.js gains featureStatusToExternalExpect -- pure, read-time lifecycle-to-issue-state derivation (PARKED -> null is the one non-obvious case). lib/feature-writer.js, lib/xref-citation.js, contracts/feature-json.schema.json -- forgejo registered as a first-class provider across XREF_PROVIDERS, validateExternalArgs, the external-link identity key, citation grammar, and its own schema conditional branch (with its own expect_labels declaration, not inherited from github's); derive_expect typed and scoped to github/forgejo only. lib/feature-validator.js -- forgejo resolution in runExternalRefChecks with the same degrade posture as github (404 -> error, everything uncertain -> skip). lib/xref-push.js -- forgejo push eligibility, derive_expect resolved from the feature's CURRENT status at push time (not a stored field), two independent state/label writes reported as {statePushed, labelsPushed, labelsAdded, errors[]} after the fix round. lib/xref-promote.js (new) + a new bin/compose.js dispatch block -- `compose roadmap promote-issue`, dry-run by default, four idempotency-checked phases under --apply (create with promoted_from provenance -> link -> label -> comment with a hidden marker), PR-backed issues refused pre-write. server/mcp-tool-defs.js -- link_features gains forgejo plus push/expect_labels/derive_expect (a real MCP capability gap independent of Forgejo). 567 tests pass across the feature's full cross-cutting surface by the end.

## What we learned

1. Concurrent Codex dispatches into the SAME working tree (not separate worktrees, per this repo's own no-worktrees convention) work fine for genuinely disjoint file sets, as long as the brief explicitly names which files each agent may and may not touch -- T4/T5/T6 ran simultaneously with zero collisions. 2. Per-task green test suites do not catch cross-task integration bugs or silent-failure UX gaps -- every one of T8's three findings existed in code that had passing tests, because each task's tests only checked its own function's contract in isolation. The design doc had explicitly called out exactly this risk (Piece 3's 'a blueprint-level test must promote a link end-to-end... not just that the individual functions accept it in isolation') and the first implementation pass still missed writing that test, which is exactly why the review-loop step of the process exists as a separate, later gate rather than being folded into each task. 3. A Codex agent's own self-report of test cleanliness needs the same verification standard as its code -- T6 volunteered, unprompted, that its CLI test had leaked a stray feature into the real checkout's ROADMAP.md and that it had cleaned it up; git status confirmed the claim was true, but the discipline of checking rather than trusting is what would have caught it if it weren't. 4. Splitting the exit-code/reporting fix (making the CLI honestly reflect write failure, including a non-zero exit code) from the label-evidence fix from the missing-test fix, then re-reviewing only the fix commit rather than the whole diff again, kept the review loop's cost proportional to what had actually changed.
