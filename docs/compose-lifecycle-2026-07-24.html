The Compose lifecycle

The Compose lifecycle is a graph

Not a pipeline with exceptions. transitions is the only authority the guard consults, and it has four branch points and a cycle. The tidy ten-step order everyone quotes lives in a different field — one that is never used to sequence anything.

The order everyone quotes is not the order anything enforces

phaseOrderThe tidy explore_design → prd → … → ship sequence is a real field, but its only production consumer is status-snapshot.js, which folds it into allKnownPhases() — a Set union across all four modes, used to check that a phase name is recognized. The order is discarded on the way in. Nothing sequences anything by it.
transitionsThis is what buildPhaseGraph reads and what every guarded transition is checked against. In it, explore_design → prd and explore_design → blueprint are two entries in the same array. Neither is the main line.
soReading the lifecycle as a pipeline with three optional steps gets the shape backwards. It is a graph with four forks, and the ten-step reading is one walk through it.

The guard graph is deliberately a superset of what the application will request — a narrower graph would reject transitions the app considers valid. That is why ship → complete and the ten kill edges are grafted on top of the declared transitions rather than written into them.

The most valuable edge in this diagram is the one that points backwards. It exists at the only moment when being wrong is still free — after the blueprint is written, before a line of code depends on it.

fix mode has the same shape and its own cycle — fix → test → fix — with three branch points and nothing skippable. plan is the only acyclic mode, and only because it is a three-node seed that no CLI command runs yet. The fourth registered mode, judgment, is not a build lifecycle at all: it is the joint state machine, and it is the branchiest graph in the system.
