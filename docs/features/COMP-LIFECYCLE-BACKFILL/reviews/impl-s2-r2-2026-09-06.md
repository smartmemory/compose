### The asymmetry between the two doors, made explicit

The backfill path deliberately keeps its re-read INSIDE the catch. A backfill holds a write-ahead
intent, and §5.11 requires a durable-write failure to refuse at `write` with the intent kept so a retry
resumes; a thrown read there would escape the gate with the intent stranded and no `refusedAt` for the
caller to act on. The live path has no intent to strand at that point and its callers have always seen
an exception. Both behaviours are now pinned by tests rather than left to the shape of a refactor.

### Which production path validates the intent against this schema

**None, today.** `contracts/lifecycle-backfill.schema.json` is referenced only from
`test/lifecycle-backfill-contract.test.js` and `test/lifecycle-backfill.test.js`
(`grep -rn 'lifecycle-backfill.schema' lib/ server/ bin/` returns nothing). Blueprint §5.7 specifies
what the intent must CONTAIN and the gate builds it field by field from `writeContext`; it does not
route the document through `SchemaValidator` on persist or on recovery. Recovery's own integrity check
is the `WRITE_CONTEXT_FIELDS` presence sweep plus the four `hasOwn` checks for the nullable fields
(R3-4), not schema validation.

So finding #1's fix is currently **enabling, not corrective**: it removes a trap that would fire the
moment any production caller does validate this schema. `test/lifecycle-backfill.test.js` "#5 —" closes
the gap from the other side by validating the intent the gate ACTUALLY persists against the production
schema through the same validator.

Wiring validation into the gate on persist would make the contract load-bearing, and it is cheap now
that the shared validator can compile the schema. It is NOT done here: it adds a refusal path that
§5.11's taxonomy does not name, which is a design decision rather than a review fix.
