## 3. Dispatch 1 — contract, strict observation and the migration executor

Own `docs/features/COMP-ROADMAP-SILENT/operation-contract.json` (new), `lib/roadmap-operation.js` (new), `lib/roadmap-operations.js` (new), `lib/roadmap-observation.js` (new), the observation addition in `lib/roadmap-parser.js` (existing), and contract inclusion in `package.json` (existing). **Registry and call ownership.** Proposed `lib/roadmap-operations.js` (new) initially declares only the migration operation and its complete obligation, modes, exclusions and empty-selection policy. It contains policy, not imports of transport handlers. Proposed `defineRoadmapOperation` in `lib/roadmap-operation.js` (new) binds that descriptor to private production observation/planning hooks and the named guarded sink at module initialization; the public migration export is the bound synchronous operation. Ordinary callers cannot pass handlers, receipts, policies or capabilities in migration options. This avoids a registry/producer import cycle and a public unguarded planning/apply export. Unknown IDs and descriptors missing policy reject before invoking a handler. Later slices extend the same registry and add asynchronous execution where required; they do not make synchronous migration return a Promise accidentally.

The executor runs **observe → account → plan → preflight → apply → verify → respond**. All preflight inputs are observed before any primary effect. It alone derives the final outcome; a handler returning empty collections without evidence is a contract violation. S1 does not claim that unconverted operations elsewhere are registered. No production test override or naked callback bypass is exposed through the public migration options.

**Parser instrumentation, not expanded grammar.** Add proposed `parseRoadmapWithCoverage` to `lib/roadmap-parser.js` (existing) by sharing its actual parsing walk with `parseRoadmap`. The existing export must retain row order, positions, status normalization, escaped-pipe handling, fence/preserved-section behavior and anonymous sentinels. Attach observations where the walk recognizes a table, falls back on an unknown header, emits a row, skips a source span, or ends in an incomplete fence/marker state. This evidence describes what the parser did; it must not infer feature statuses or dependencies from prose.

Before accepting a table as supported migration input, check that its header expresses a documented feature-row layout and status column, its divider and cells are usable, and each named row satisfies the migration contract. The current layout fallback is not sufficient. Distinguish explicit anonymous placeholders in an otherwise supported feature table from unrecognized strings transformed into anonymous sentinels. Only the former are declared exclusions. Duplicate/conflicting named targets, invalid statuses/codes, malformed tables and unexplained skipped spans remain unresolved; they cannot be silently counted as exclusions.

**Conservative coverage recommendation, pending Q1:** source containing unclassified prose or feature-heading narrative is indeterminate even alongside some valid table rows. Feature-looking headings cannot be classified as harmless milestone metadata merely because the old parser treats them that way. Recognize only bounded table-document structure for adequate coverage: blanks, the document title, supported phase/milestone scaffolding whose meaning is unambiguous, supported tables, and explicitly excluded balanced code/preserved blocks. Do not classify an arbitrary heading-only document as a proven empty roadmap. Empty bytes or an explicitly supported empty table with fully accounted surrounding structure can be no-change. A non-feature table is unresolved unless its exclusion is explicitly defined by operation policy. Do not use counts, a percentage cutoff or the narrative ownership flag as a substitute for observation.

`lib/roadmap-observation.js` (new) strictly reads optional project configuration, required roadmap bytes and planned destinations. Distinguish ENOENT from other errors with read/stat evidence; no exists-then-null success rule. Resolve paths with `lib/project-paths.js` (existing) and `lib/paths-core.js` (existing) only after configuration is adequately observed. Preserve configured artifact roots and explicit migration options. Present malformed config, unsupported grammar, read failure and corrupt existing records as indeterminate with bounded source locations, resolved paths and total unresolved counts. Missing required roadmap is also indeterminate. An absent optional config and absent new destination are valid, separately recorded observations.

Remediation in S1 names the actual unresolved source/location, asks for a supported and unambiguous table representation or repair of the specific read/config failure, then instructs a dry-run retry before application. It must not promise that prose conversion is automatic, suggest deleting canon, recommend generating over the source, or advertise inspect before S3 ships. No new force/allow-empty escape hatch is introduced.

## 4. Dispatch 2 — migration planning, guarded effects and real CLI outcomes

Own `lib/migrate-roadmap.js` (existing), the guarded migration write entry and shared preparation in `lib/feature-json.js` (existing), `lib/roadmap-operation-cli.js` (new), and only the migration branch in `bin/compose.js` (existing). Extend `test/migrate-roadmap.test.js` (existing), create `test/roadmap-migrate-cli.test.js` (new), and update only the moved migration allowance in `test/completion-write-allowlist.test.js` (existing).

**Public entry and whole-plan observation.** Keep `migrateRoadmap` synchronous and route all its calls through the bound executor. It must not call itself via the registry or expose the old write loop as an alternate public export. The CLI resolves the workspace as today and submits the existing dry-run/overwrite options. Remove its independent permissive external-prefix load; the operation observes configuration before deriving configured exclusions. Explicit library option overrides still participate in the observed policy. Configuration/source/destination fingerprints and the normalized workspace binding belong to one execution, not global mutable state.

Observe the complete source before planning any write. For each supported named row: account an explicit external exclusion first; otherwise observe the exact destination. A readable existing record without overwrite is excluded as already present/not compared. A malformed or unreadable existing destination is unresolved even without overwrite; do not treat it as new or silently certify it as a valid existing record. This is stricter than the nullable reader and is deliberate. Plan no primary writes if any required source/target remains unresolved.

For eligible creates/overwrites, preserve current metadata merge precedence and phase extraction from `lib/migrate-roadmap.js` (existing); do not turn this feature into a metadata migration redesign. Compare the intended semantic record with the observed record before applying. Identical semantic content, formatting-only changes and date-only changes produce no-change and leave bytes untouched. Capture the operation date once for genuinely changed candidates. Reject conflicting duplicate row targets before any write; do not make parser order silently choose a winner. Validate all prepared records and existing link preconditions before starting the batch, then recheck mutable prerequisites at each sink.

**Guard at the actual effect.** Introduce proposed `prepareFeatureWrite` and `writeMigrationFeature` in `lib/feature-json.js` (existing). Share the existing serialization and atomic replacement implementation rather than duplicating it in migration. Ordinary `writeFeature` callers retain their validation/default behavior; the migration entry requires executor authorization unconditionally. PreparedFeatureWrite in the new contract owns the serializable preparation boundary. No public option may turn off migration authorization or link validation.

The executor mints authorization only after full preflight. The migration sink checks private capability identity and the bound workspace, operation, target, source/config/destination observations and prepared candidate before directory creation or temporary writes; recheck before final replacement. Authorization covers only declared destinations, including absent destinations and configured external roots. It cannot be replayed for another target, workspace or later execution. A stale source or destination invalidates the outstanding effect. No handler-provided count or flag can bypass these checks. Direct calls to the guarded migration sink without valid capability refuse before filesystem mutation.

Perform actual writes through the shared temp-and-rename primitive with preserved link guards and cleanup behavior. Reopen the destination and verify planned bytes and semantic state before emitting an EffectReceipt. Count changed feature records/files using the contract's units; directory creation, warning output, update-date stamping and temporary-file activity are not successful feature migration. Byte comparison and receipt creation belong to the runtime/sink, not CLI formatting.

These checks address accidental stale observations through covered calls; they are not a claim of filesystem-wide transactional isolation against unrelated concurrent writers. Recheck observations at the real replacement boundary, stop on observed drift, and retain verified earlier receipts. Do not claim whole-batch rollback or protection from unconverted raw writer APIs. Broad sink/discovery closure remains S7.

**Outcome derivation and failures.** Adequate coverage with only declared exclusions or equal records is no-change. A nonempty validated dry-run is planned with no applied receipts; an empty valid dry-run is no-change. A completed nonempty batch with all planned semantic effects verified is applied. Unknown input/read/coverage before effects is indeterminate. Known invalid authorization or stale precondition before effects is refused. A write/verification failure with no verified durable effect is failed, preserving uncertainty about possible writes; after any verified effect, an unresolved/failed required remainder is partial with those receipts and the exact unverified retry scope. Stop rather than continue after a migration sink failure. Never call a failed readback an equality, never infer rollback, and never drop a verified first effect when the second write fails.

**Completion exemption remains specific.** Preserve the existing named create/overwrite historical COMPLETE exemption only when an actual semantic write is about to be attempted after authorization and guards. A dry-run or equal overwrite must not log that a completion was written. A changed overwrite to COMPLETE still logs the overwrite exemption, and a new COMPLETE row logs create. Do not introduce a general completion bypass in the shared writer. The existing completion allowance follows the actual guarded migration path with an exact reason; all unrelated allowances and stale-entry checking remain intact.

**One migration transport renderer.** Proposed `renderRoadmapOperationCli` in `lib/roadmap-operation-cli.js` (new) consumes OperationResult, Diagnostic, MigrationCompatibilityResult and TransportMapping. `bin/compose.js` (existing) prints and exits from that mapping for migration: applied/no-change/planned use 0, indeterminate 2, refused 3, failed 1, partial 4. The adapter also implements the design's observed assertion mapping for later consumers, without inventing a migration assertion mode. Do not add a migration JSON flag or a new migration server endpoint merely for tests.

Human output leads with the outcome, then verified versus planned work, exclusions, unresolved source/target evidence and valid remediation. Never print created/updated claims from dry-run plans. Library callers receive the mandatory outcome and preserved compatible collections; the CLI must not reduce a returned failure to success because the call did not throw. Unexpected exceptions still produce a nonzero failure with the underlying cause, preserving any finalized operation evidence. Other roadmap branches keep their current behavior until their owning slice.

## 8. Owner questions — ALL FOUR RULED 2026-09-12; retained for provenance

**All four were ruled by the owner on 2026-09-12; every ruling adopted the blueprint's recommendation.** They are settled inputs to implementation, not open items — do not re-litigate them in a dispatch. Q1 and Q2 were decided by the owner directly; Q3 and Q4 were engineering defaults ruled by the controller and confirmed unobjected.

1. **Q1 — how conservative may first-slice migration coverage be?** The design requires unknown spans to prevent migration but also defers prose grammar to PROSE-READ. **Recommendation:** S1 accepts demonstrably supported table documents and explicit exclusions, and reports mixed/unclassified prose as indeterminate before all writes. Instrument the existing parser; do not build a second parser or use the narrative flag alone. This deliberately trades migration availability for truthful coverage until recognition improves. An alternative that permits arbitrary ignored prose needs an explicit exclusion contract and its own negative controls, not a local heuristic.
   **RULING 2026-09-12 (owner): REFUSE.** S1 accepts demonstrably supported table documents with explicit exclusions, and reports mixed or unclassified prose as indeterminate before any write. The owner accepted the stated trade: `compose roadmap migrate` will now visibly stop on documents where it currently exits zero while writing nothing. Instrument the existing parser; do not build a second parser and do not rely on the narrative flag alone.
2. **Q2 — what exactly is the compatibility period?** The design says one period without specifying its duration, and existing tests rely on planned/equal writes populating created/updated. **Recommendation:** keep legacy collection names for the next released minor-version interval, document that they now contain verified applied work, and expose dry-run intent through the contract. Correct false success immediately. Revisit removal only in a separately announced compatibility change; do not select a speculative version number here.
   **RULING 2026-09-12 (owner): ONE MINOR VERSION, DOCUMENTED.** Keep the legacy `created`/`updated` collection names for the next released minor-version interval, but populate them only from verified applied receipts, and document the changed meaning in CHANGELOG at release. False success is corrected immediately; only the naming lingers. Rewrite the existing dry-run and equal-overwrite assertions in `test/migrate-roadmap.test.js` explicitly rather than deleting them. Do not select a speculative version number in the blueprint.
3. **Q3 — should S1 repair the shared row-position schema mismatch?** The parser starts at zero; the existing row schema starts at one. **Recommendation:** no cross-domain schema/index change in S1. Define MigrationParsedRow in the new contract with the producer's ordinal convention and reuse only compatible constraints. File shared-schema convergence separately; require the actual first generated row as a positive test. If the owner chooses global normalization, re-scope its consumers before implementation.
   **RULING 2026-09-12 (controller): NO — DEFER.** Verified independently against source: `lib/roadmap-parser.js:60,178` initializes position at 0 and post-increments; `contracts/roadmap-row.schema.json:21` requires `minimum: 1`. Shared-schema convergence is follow-up 1, not S1 work. Require the actual first generated row as a positive test.
4. **Q4 — does read-only inspect forbid temporary persistence too?** The existing canonical collector creates a temporary VisionStore and writes during collection. **Recommendation:** S3 inspect should perform no filesystem mutation, including temporary stores; supply an in-memory ephemeral store implementation to the real seed/adapter path.
