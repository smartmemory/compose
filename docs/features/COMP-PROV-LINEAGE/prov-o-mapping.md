# COMP-PROV-LINEAGE — PROV-O term mapping

**Status:** written before schema work (AC #1). **Spec read:** W3C PROV-O,
<https://www.w3.org/TR/prov-o/> (2013-04-30 Recommendation), 2026-08-09.

This records how the W3C PROV-O vocabulary maps onto Compose's existing
lifecycle concepts, so the lineage fields we add are named after a standard
rather than invented. We borrow the **vocabulary only** — no RDF stack, no
triple store, no SPARQL, no JSON-LD runtime (per plan "out of scope").

## PROV-O core (what the spec actually says)

Three "starting point" classes and the properties that connect them. Domain →
range is the direction the property points (subject → object).

| Term | Domain → Range | PROV-O definition (abbreviated) |
|---|---|---|
| `prov:Entity` | — | a thing with fixed aspects (physical, digital, conceptual) |
| `prov:Activity` | — | something occurring over time that acts upon / with entities |
| `prov:Agent` | — | something bearing responsibility for an activity or entity |
| `prov:wasGeneratedBy` | Entity → Activity | completion of production of a new entity by an activity |
| `prov:used` | Activity → Entity | beginning of utilizing an entity by an activity |
| `prov:wasDerivedFrom` | Entity → Entity | transformation / update / construction of one entity from another |
| `prov:wasAttributedTo` | Entity → Agent | ascribing an entity to an agent |
| `prov:wasAssociatedWith` | Activity → Agent | responsibility of an agent for an activity |
| `prov:actedOnBehalfOf` | Agent → Agent | delegation of authority between agents |
| `prov:wasInformedBy` | Activity → Activity | one activity used an entity generated by the other |
| `prov:startedAtTime` / `prov:endedAtTime` | Activity → xsd:dateTime | when an activity started / ended |

## Compose concept mapping

| PROV-O class | Compose concept | Concrete identity |
|---|---|---|
| `prov:Entity` | a lifecycle **artifact** | `design.md`, `prd.md`, `architecture.md`, `blueprint.md`, `plan.md`, `report.md` (canonical, auto-discovered under the feature folder) plus registered non-canonical `artifacts[]` entries |
| `prov:Activity` | a lifecycle **phase** | `explore_design`, `prd`, `architecture`, `blueprint`, `verification`, `plan`, `execute`, `report`, `docs`, `ship` (from `lib/lifecycle-modes.js` `phaseOrder`) |
| `prov:Agent` | the **agent/model** that ran the phase | e.g. `claude`, `codex`, an agent string (deferred — see below) |

### Property mapping (what we adopt now)

| PROV-O property | Compose meaning | Populated by | Notes |
|---|---|---|---|
| `wasGeneratedBy` | which **phase** produced this artifact | lifecycle writers | The phase is the Activity. `blueprint.md` wasGeneratedBy the `blueprint` phase. Matches the existing `edgeEvidence` map (`explore_design->blueprint: design.md`, etc.) inverted. |
| `wasDerivedFrom` | which **upstream artifacts** this artifact was built on | lifecycle writers | The load-bearing edge for staleness. `plan.md` wasDerivedFrom `blueprint.md` wasDerivedFrom `design.md`. Entity → Entity, so staleness is graph reachability over this relation. |
| `used` | which upstream artifacts the phase consumed | (implied) | Activity → Entity. For our fixed chain this is the inverse of the downstream artifact's `wasDerivedFrom`; we do not store it separately in v1 — it is recoverable. |

### Deferred (named now so a later rename is unnecessary)

| PROV-O property | Why deferred |
|---|---|
| `wasAttributedTo` (Entity → Agent) | We do not reliably capture which agent authored each artifact yet. When we do, the field name is already chosen. |
| `wasAssociatedWith` (Activity → Agent) | Same — phase-to-agent responsibility is not tracked structurally today. |
| `actedOnBehalfOf` (Agent → Agent) | No delegation graph in Compose. |
| `wasInformedBy` (Activity → Activity) | Phase-to-phase is derivable from artifact edges; not stored. |
| `startedAtTime` / `endedAtTime` | Phase timing lives elsewhere (GSD timing); not part of the lineage edge. |

## The one real design decision: where lineage lives

**Verified gap** (feature.json description, confirmed against
`contracts/feature-json.schema.json`): `artifacts[]` entries carry only
`{type, path, status}` and are explicitly for **non-canonical** artifacts.
Canonical artifacts (`design.md`, `plan.md`, …) are **auto-discovered, not
registered**, so there is no existing record on which to hang a lineage edge.

Two candidate homes:

1. **Embedded marker in the artifact** — extend the existing
   `<!-- phase: <name> -->` convention that `lib/staleness.js` already reads
   from the first 5 lines. Add a sibling `<!-- wasDerivedFrom: design.md -->`.
   - Pro: canonical artifacts stay unregistered; no schema for auto-discovered
     files; lineage travels with the file.
   - Con: parsing markers, not structured JSON.

2. **A `lineage` block in feature.json** keyed by artifact filename.
   - Pro: structured, queryable without reading every artifact.
   - Con: reintroduces a registration burden for auto-discovered artifacts and
     can drift from what is on disk.

**Chosen: option 1 (embedded markers), reusing the `staleness.js` precedent.**
The derivation chain for canonical artifacts is fixed and small, the marker
convention already exists and is already parsed, and it keeps the "canonical
artifacts are not registered" invariant intact. The reachability query reads
markers the same way `checkStaleness` already reads the phase marker. A
JSON-LD export stays possible later by walking the same edges — the vocabulary
is standard regardless of storage.
