## 2. New contracts and internal shape boundaries

Four schema files: existing `contracts/routing-start.schema.json` and `contracts/routing-record.schema.json`, plus `(new)` `contracts/routing-join.schema.json` and `contracts/routing-outcome.schema.json`. Extend the loader at `lib/routing-ledger.js:9–18` to compile their closed tagged unions and the separate receipt-detail definition below. Retain `_source`, `_roadmap`, schema versions and required explicit nulls. All new journal data uses record branches: `validateRoutingJournal` rejects new top-level routing keys (`lib/routing-ledger.js:372–374`). Common record fields below are `{type, schemaVersion, startId, rootDigest, id}`; every reference is validated on write and reload against its original run/root. `(new)` shapes and methods here are plans, not existing APIs.

**RoutingJoin v1 — call evidence branches.**

- `call-intent`: common fields plus `{ownerRunId, ownerJournal, issuanceId, observationId, recordId, parentRecordId, callSlot, callId, callIdSource, purpose, transport, intendedAt, profileIntent}`. Exactly one of `issuanceId` and `observationId` is non-null. Supported primaries reference their issuance; unsupported calls reference the observation branch below. `purpose` is `primary|normalization-repair|auxiliary`; failure usage resolves the SAME call, never creates another launch. `transport` is `mcp|local-sdk`. `profileIntent` is configured provider/model/effort, never executed evidence. `callSlot` is a durable binding-local invocation slot, not global arrival order. Persist the connector-minted callId/source in the intent as well, so loss of the return cannot lose its identity; a missing identity stays null/absent. Intent completes before launch.
- `call-resolution`: common fields plus `{intentId, sequence, previousResolutionId, outcome, callId, callIdSource, launchOutcome, reportedModel, reportedEffort, usageEvidence, usageRef, terminationEvidence, resolvedAt, incompleteReasons}`. `outcome` is `resolved|errored|unresolved`; `callIdSource` has ONLY `connector-invocation|absent`, paired respectively with a nonempty `callId` or null. `launchOutcome` is `not-executed|executed|uncertain`, independently witnessed by transport progress/return/error; a minted id does not choose it. `usageEvidence` retains raw values, field-presence flags and provenance, with null for missing tokens/time/USD/model/effort; `usageRef` identifies the owner-run receipt and canonical payload digest, or null. `terminationEvidence` records return, acknowledged transport termination or uncertainty bound to this intent/call. Local effort stays null: configured `appliedEffort` is not reported execution (`lib/local-claude-connector.js:151,287–307`).
- `unsupported-observation`: common fields plus `{recordId, source:'unsupported', unsupportedReason, ownerRunId, ownerJournal, issuanceId:null, issuanceToken:null, parentRecordId, parentIntentId, scopedStep, stage, epoch, itemIndex, generation, logicalWaveId, logicalTaskId, itemBindingRef, evidenceSource, evidenceRef, observedDispatchToken, incompleteReasons}`. Reasons include `engine-fanout`, `engine-judged`, `multi-stage-consumer`, `normalization-repair`, `gate-qa`, `review-fixer`, `codex-preflight`, `scoped-fixer`, `policy-revision`, `bug-escalation` and `engine-evidence-unavailable`. Physical/logical fields and parent refs are nullable when genuinely unavailable. An observed engine token is retained only as evidence, never an invented routable issuance. `evidenceSource` distinguishes connector, engine-receipt and engine-audit; missing evidence remains explicit. Connector observations use a namespaced root/owner/call-slot identity; engine receipts use a namespaced owner-run/receipt-id identity, with receipt sequence/digest cross-checks. `legacy:<seq>` is a receipt reference, never `callId`. A no-receipt engine coverage record binds the known run/scoped step/stage/epoch and reports unavailable evidence without asserting a model launch or zero cost.

**Resolution lifecycle.** Each resolution is immutable by id; the evidence chain is append-only, not exactly-once resolution. Allocate contiguous sequence numbers under the owner-journal writer, derive id from intent/sequence, require the previous id and validate the entire chain. Persist a `call-evidence-head` record with `{intentId, sequence, resolutionId, previousHeadId, count}` in the same durable mutation as each resolution (common fields apply); validate head and predecessor chains on reload and retain expected heads in materialization/continuation evidence. No untyped routing subtree; reject gaps, forks and missing expected tails. Latest selection follows validated sequence, never timestamps or arrival order. Recovery may append `unresolved`; genuine late connector completion/error, acknowledged termination, previously missing raw usage/provenance, or receipt acknowledgement may subsequently improve it. A non-null identity, known cost/model/effort, confirmed non-execution, or confirmed terminal result cannot be overwritten by contradictory evidence. Repeated evidence is a no-op; changed bytes at the same id, changed call ownership, competing connector ids, executed-after-confirmed-not-executed, or success/error conflict refuses `ROUTING_CALL_EVIDENCE_CONFLICT`. Receipt acknowledgement is separate delivery evidence: it does not rewrite an already spooled payload. Reload and continuation read the authoritative owner's latest chain, so an inherited unresolved copy never masks a late completion.

**RoutingOutcome v1 — capture and derivation branches.**

- `wave-snapshot`: common fields plus `{runId, revisionDigest, gateStepId, gateToken, capturedAt, resetTarget, resetClosure, sourceRefs, waves, ordinaryIssuances, priorSnapshotIds}`. Each wave carries `{runId, scopedStep, stage, epoch, logicalWaveId, logicalEpoch, epochBindingId, sourceRef, items}`; each item retains `{logicalTaskId, fullItem, itemDigest, itemIndex, generation, stage, status, admissionId, issuanceId, issuanceToken, acceptedDispatchToken, chosenTier, executedTier, priorSnapshotId}`. Keep complete source contents/digests or immutable retained refs; item admission/issuance/tier/token fields may be null for skipped or unissued entries. Ordinary rows use explicit null item/generation/task fields and retain their admission, epoch and issuance refs. `executedTier` is `{value, source, evidenceRefs}` with nullable value, derived from genuine primary execution evidence and pinned mapping only.
- `gate-disposition`: common fields plus `{snapshotId, runId, gateStepId, gateToken, gateOrdinal, requestedDecision, finalProposedDecision, findingsRef, dispositions, partitionCheck, ownershipCheck, lineage}`. It is written after merge adjustments and before RPC. Lineage relations `retained|repaired|re-implemented|added` bind from/to snapshot, admission and issuance ids plus logical identities; nullable future issuance references bind to a retained proposed-task digest and are completed by a later immutable lineage record. Task strings or indices alone cannot select historical work.
- `gate-acknowledgement`: common fields plus `{dispositionId, requestDigest, witness, reconciliation, acknowledgedAt}`. Reconciliation is `token-response|token-engine-witness|ordinal|unconfirmed`; witness retains the response or exact audited engine provenance with identity checks. Append later evidence under new ids; conflicting decisions/rounds refuse, and ordinal evidence cannot become token evidence merely by copying a prepared transaction token.
- `lineage-link`: common fields plus `{dispositionId, relation, fromSnapshotId, fromAdmissionId, fromIssuanceId, proposedTaskDigest, toSnapshotId, toAdmissionId, toIssuanceId}`; added work has null predecessor refs, and a future target issuance remains null until a later linked record supplies it. Validate both endpoints against retained full-item digests and logical wave/epoch identities; a task-name match alone is insufficient.
- `outcome`: common fields plus `{issuanceId, previousOutcomeId, evidenceRefs, label, binary, derivation, censorReason}`. One latest validated classification per issuance, with immutable evidence-derived revisions rather than rewriting an unknown outcome. Labels and binary dispositions are specified in section 4. Conflicting unsupported assumptions never complete a row.

**Receipt detail is its own schema.** Define a closed `$defs.receiptRouting` in RoutingJoin, compile a dedicated validator and validate `detail.routing` against it, NOT against `call-intent` or `call-resolution`. Fields: `{schemaVersion, kind, startId, rootDigest, ownerRunId, recordId, issuanceId, issuanceToken, observationId, parentRecordId, intentId, callId, callIdSource, scopedStep, stage, epoch, itemIndex, generation, logicalTaskId, logicalWaveId, admissionId, itemBindingRef, selectedRouteRef}`. `kind` is `route-metadata|paid-call`. Metadata has a supported issuance and null observation/intent/call fields with `callIdSource:absent`; paid calls require an intent and the genuine connector id, with either supported issuance or unsupported observation linkage. Unknown unsupported context fields are null; a missing call id produces local incomplete evidence, never a fabricated paid receipt. Receipt detail contains stable identity refs, not mutable resolution/delivery state.

**Ledger row v1 `(new branch in contracts/routing-record.schema.json)`.** `{schemaVersion, startId, rootDigest, recordId, version, materializedAt, source, key, context, issuance, observation, outcome, evidenceRefs, calls, cost:{tokens,durationMs,usd,provenance,paidReceiptRefs}, completeness:{state,reasons}}`. Supported rows have issuance, unsupported rows have observation and null issuance; both retain known excluded spend. Incomplete rows are WRITTEN. Source exclusions, receipt ownership and inclusive child costs are explicit, so observations cannot duplicate samples or costs.

**`context` — the repair stratum, recorded because it cannot be recovered later.** `{waveKind, repairOfRecordId, repairDepth, repairLineageRefs}` where `waveKind ∈ {fresh, repair, retry, unknown}`. Without it a repair-wave sample is indistinguishable from a fresh-wave sample once it reaches the ledger, and the journal that could re-derive it is per-run, per-artifact-root and not retained for the ledger's lifetime (`lib/consumer-fanout.js:282–296`). Design already scopes the eligible population by “key/tier/cohort and source stratum” (`docs/features/COMP-MODEL-ROUTE/design.md:296–298`); this is the field that makes the repair stratum expressible. Provenance: RECOMPUTED at materialization from persisted journal records — `waveKind` from the admission's recorded epoch and `repairContext` (`lib/build.js:1060`, currently `{state:'not-evaluated-s1a'}`), `repairOfRecordId`/`repairLineageRefs` from the `lineage-link` whose `relation` is `repaired` and whose `toIssuanceId` is this row's issuance — then frozen into the row, which IS the durable sample. It is never derived from in-memory state and never inferred from a task name. `repairDepth` counts validated repair hops so a third-round repair is not silently pooled with a first attempt. Ambiguous or missing lineage yields `waveKind:'unknown'` with null refs, which is censored like any other unknown — never defaulted to `fresh`. **S1b RECORDS this and nothing more:** no floor is computed, compared or enforced here, and no stratum-conditioned policy exists until S3 (see Q3).

**Internal reader inventory.** Update record validation/dispatch in `lib/routing-ledger.js:369–455`, call-chain/outcome/receipt-detail validators `(new)`, safety projection `routingIssuanceState` (`:457–488`), journal reload (`lib/consumer-fanout.js:467–530`) and mutation methods (`:717–775,850–872`). Preserve S1a successful settlement equality; add only section-4 failure and cancellation proof branches. `exportRoutingJournal`/`readRoutingRecord` (`:741–751`) keep their return contracts but validate new references. Continuation initialization (`lib/routing-ledger.js:325–340`) retains ancestry, NOT the pending receipt spool: add a root-bound `receipt-owner` record (RoutingRecord branch) with common fields plus `{ownerRunId, revisionDigest, journalLocator, runBindingId}`, validate its path and retain access across continuation. Receipt-owner traversal, engine-receipt ingestion, ledger materialization and latest-version selection are new readers. Never apply immutable journal-id rules to ledger versions.

## 3. D5 — call observation and receipt joins

**Immutable binding, one intent owner.** Add `(new)` `bindRoutingCalls` in the routing module, returning an immutable per-issuance observer bound to start/root, owner run/journal, original descriptor, admission, issuance and record id. Construct it where the consumer issuance is discovered (`lib/build.js:1570–1575`), and at ordinary issuance preparation in Build (`lib/build.js:4762–4764`) and GSD (`lib/gsd.js:646–648`). Separate run-bound observers cover unsupported auxiliary calls without an issuance. No mutable “current issuance” on shared context/client: Build shares them (`lib/build.js:4452–4470`) and overlaps consumers (`:4510–4536`). Context may hold a factory, never the active binding.

**Choose the connector invocation boundary as the sole intent-owning layer**, implemented by MCP `#dispatchAgentRun` (`lib/stratum-mcp-client.js:268–298`) and local `runLocalClaudeAgent` (`lib/local-claude-connector.js:213–217`). This sees success/error and raw telemetry for direct and normalized calls alike. Allocate the binding-local slot and connector wrapper id once, await durable `intent`, then invoke; append resolution/termination and raw usage before returning or rethrowing. Stable slot identity uses the originating descriptor plus call-site/purpose and its durable per-binding invocation counter; child slots reference their parent intent, never connector arrival order. Recovery reuses the persisted slot and never dispatches merely because it lacks completion. The normalizer primary/repair forks (`lib/result-normalizer.js:563–599,777–816`) and `runAgentText` (`lib/stratum-mcp-client.js:831–895`) only pass bindings/child purpose and supplementary evidence; neither creates a duplicate intent. Internal observer options are stripped before request/SDK construction and never reach prompts, provider options or telemetry sent upstream. Nonparticipating calls omit the options and observer work altogether.

**Call identity and evidence.** The once-minted connector wrapper id is `callId` for BOTH transports, on success and error (C11). Capture it before later normalizer/receipt fallbacks can replace a lost id. MCP capability/abort refusal before its RPC (`lib/stratum-mcp-client.js:312–332`) is `launchOutcome:not-executed` with `callIdSource:connector-invocation`, not absent identity. Raw provider response/progress and termination evidence decide execution; unknown launch completion stays uncertain. Preserve local raw field presence from capture rather than zero-started return defaults; record reported model independently from configured model and local effort as null. A call without returned usage stays visible and incomplete even with a valid id; no fallback UUID, issuance token, synthetic legacy id or zero-fill can complete it.

**Q3 — is the repair floor measuring the right thing? (OPEN, owner-raised 2026-09-11; S3 decision, not S1b).**
Decision 7 makes the floor a TIER comparison: never route a repair below the rung that executed. That treats ladder
position as a proxy for “likely to succeed on this work”, and the owner's objection is that the proxy inverts — a
stronger model can follow a tightly-specified task WORSE (over-reasoning, widened scope, ignored constraints), so
`critical` is not always the safer redo. Half the objection is already handled: cross-provider evidence refuses
admission and provider ladders are explicit policy rather than a global ordering of tier names
(`design.md:318,350–353`), and `coordinator` is not a rung. What is NOT handled is within-provider monotonicity.
The tension is structural, not cosmetic: the floor applies after EVERY source and rejects anything below it
(`design.md:320–322`), so it OVERRIDES the learned value. A feature whose premise is “stop assuming which model is
right, measure it” hardcodes one prior and then lets that prior outrank the measurement. If the evidence ever shows
a lower rung with a better accepted-rate on a key, the floor blocks acting on it.
Candidate shape (NOT ruled): make the floor evidence-based where durable evidence exists — never redo with a
candidate whose measured accepted-rate is worse than the executed one's — evaluated on the REPAIR STRATUM rather
than the key overall, since work that reached a repair is not a random sample of that key; keep the ladder as the
cold-start prior when the repair stratum lacks durable evidence; keep cross-provider refusal unchanged; and derive
the floor from the same evidence as the learned source so the two cannot contradict, leaving it to constrain the
genuine priors (manual, preset, spec default). Counter-argument to weigh: a second independent rail is worth having
when evidence is thin — though if the durability bar (breadth ≥3 runs, ≥2 workspaces) is too weak to route repairs,
it is too weak to route anything, and that bar is the knob rather than the ladder.
**Do not decide this now.** S1b's `context` field makes the repair stratum measurable; the shadow corpus should
settle it before S3 implements enforcement. Nothing in S1b depends on the answer — recording what executed is
correct under either rule.
