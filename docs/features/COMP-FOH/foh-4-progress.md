## Phase 1 exploration — FEASIBILITY RESOLVED (probed directly; explorer agent died on API error mid-run)

### Q1 — SmartMemory conviction surface: VERDICT (a) READY end-to-end
"Conviction" in SmartMemory = a per-item **confidence** scalar (0.0–1.0) with a **decay history**.
- Base `MemoryItem` carries `confidence: float = 1.0` (`smart-memory-core/.../models/memory_item.py:74`, set :215, serialized to metadata :347). EVERY fluid record already has it (default 1.0).
- `ConfidenceManager` (`.../reasoning/confidence.py`): `apply_decay(item_id, decay_factor, reason, conflicting_fact)` — item-id addressed, works on ANY item (`self.sm.get(item_id)`), drops `metadata["confidence"]`, appends a `decay_event` to `metadata["confidence_history"]` (capped 20), sets `challenged`/`challenge_count`/`last_challenged_at`, persists via `self.sm.update(item)`. `get_history(item_id)` reads `metadata["confidence_history"]`.
- HTTP surface (`smart-memory-service/.../routes/reasoning.py`): `GET /memory/reasoning/confidence-history/{item_id}` (:311), `GET /memory/reasoning/low-confidence` (:268), `POST /memory/reasoning/resolve` (:142, applies decay), plus FOH-3's `POST /memory/reasoning/challenge` (:85, detection only).

### Q2 — Reachability vs our fluid_<kind> data: MIXED (one safe path, one trap)
- **SAFE:** `GET /confidence-history/{item_id}` is item-id addressed → reaches any fluid record by handle, NO memory_type filter. Same for current confidence (on the item, returned by getRecord).
- **TRAP (FOH-3 déjà vu):** `GET /low-confidence` calls `self.sm.search("", memory_type="semantic")` (confidence.py:96) — the exact-type post-filter. Default "semantic" = ZERO fluid hits; would need `memory_type="fluid_<kind>"` per kind. Same silent-no-op class FOH-3 hit.

### Q3 — MEANINGFUL SIGNAL? **NO, not read-only. This is the load-bearing finding.**
Confidence only MOVES via `apply_decay`, and `apply_decay` is invoked ONLY from the **resolve** path (`challenger.py:329 resolve_conflict` / `auto_resolve`, e.g. strategy ACCEPT_NEW → decay_factor 0.5). The plain `challenge()` method (challenger.py:202) DETECTS conflicts and returns them — it does NOT decay. **FOH-3 wired `/challenge` (detection only), so nothing in Compose's flow moves a fluid record's confidence today.** A read-only `conviction(handle)` would return a flat **1.0 with empty history for every record** — the exact "green endpoint, dead capability" failure FOH-3's own report flagged as the lesson.

### DESIGN FORK (for owner gate)
- **v1a — read-only conviction (thin):** `conviction(handle)` = current confidence + `/confidence-history`. Pure wiring (mirror FOH-2/3), but honestly flat 1.0 today. Ships a dead capability unless disclosed hard. NOT recommended alone.
- **v1b — conviction + the decay loop (meaningful):** FOH-3 already detects conflicts; FOH-4 calls `POST /resolve` on a resolved conflict so the contradicted record's confidence actually drops, and `conviction(handle)` reflects it. Connects rung-4 (challenge) → rung-5 (conviction) into a real loop. Cost: it MUTATES stored state (heavier than read-only FOH-2/3), bigger slice, and introduces a resolution decision (ACCEPT_NEW/KEEP_EXISTING/... = the gate/flag/skip autonomy dial — who decides?).
- Both endpoints exist and are Compose-side reachable → NOT blocked on SmartMemory work either way.

### `/resolve` contract VERIFIED (advisor-flagged; read reasoning.py:142-213)
- Request `ResolveRequest`: `{existing_item_id, new_fact, auto_resolve, strategy?, use_wikipedia, use_llm}`.
- **Item-id addressed** — `smart_memory.get(body.existing_item_id)` then builds a Conflict from `existing_item.content` + `new_fact`. **NO memory_type re-detection → no FOH-3 trap on the write path.**
- `auto_resolve:false` + explicit `strategy` + `use_llm:false` = deterministic, no LLM cascade, no Wikipedia → no 30s-timeout need. `auto_resolve:true` runs the Wikipedia→LLM→grounding→recency cascade (defer to later).
- Scoped via `create_secure_smart_memory(scope)` — workspace-bound like challenge/searchItems.
- Decay magnitude: strategy `ACCEPT_NEW` → `apply_decay(existing_item_id, decay_factor=0.5)` (challenger.py:377) → confidence -= 0.5 (floor 0.0), one history event (cap 20). Chunky, near-irreversible.
- **No ChallengeResult seam change:** FOH-3 `Conflict` exposes `handle` (raw `existing_item_id` mapped away, provider.js:478 + smartmemory-provider.js:1193). v1b resolves handle→item_id internally (provider already does the inverse via getItem) and derives `new_fact` from the challenged record's `assertion`. v1b write signature: `resolveChallenge(challengedHandle, conflictHandle, strategy)`.

### Recommendation (pending owner)
Lean **v1b but minimal**: ship `conviction(handle)` (read) + a single, explicit `resolveChallenge(handle, strategy)`-style write that decays via `/resolve`, gated (human/agent picks the strategy — no silent auto-resolve in v1). That makes conviction non-trivial from day one and honors "no dead paths." Defer `/low-confidence` "stale beliefs" surface (has the type-trap; needs per-kind fan-out) to a later slice.
